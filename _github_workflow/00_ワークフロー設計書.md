# GitHub × Cursor 協働ワークフロー設計書

> ビジネスサイドはCursorだけ。エンジニアはGitHubで。
> プロジェクトの中心に「動くコード」を置き、二つの世界をシームレスにつなぐ仕組み。

---

## 全体像

```

                    共有リポジトリ
                    コードが真実の源泉
```

## コンセプト: コードを中心に据えた協働

### なぜ「コードが中心」なのか

| 従来のやり方 | この仕組み |
|-------------|-----------|
| 仕様書を書く → 認識ずれ → 手戻り | **動くものを見て**確認 → 正確なFB |
| テキストだけで要望を伝える | **コード改善案**で具体的に提案 |
| 完成するまで何もわからない | **デモで毎週進捗を確認**できる |
| フィードバックが散らばる | **1つのリポジトリに全部集まる** |

### ビジネスサイドの3つの武器

| 武器 | 何をするか | どうやるか |
|------|-----------|-----------|
| **🖥️ デモ確認** | 今の状態を目で見る | `demo/index.html` をブラウザで開く |
| **💬 テキストFB** | 言葉で要望を伝える | Cursorに話しかけてフィードバックを記録 |
| **💻 コード改善案** | 具体的なコードで提案する | CursorのAIに作ってもらう |

## プロジェクトのディレクトリ構造

```
projects/
├── [プロジェクト名]/
│   ├── README.md                         ← プロジェクト概要 + 機能実装状況
│   │
│   ├── app/                              ← 🔧 実際のコード（プロダクト本体）
│   │   ├── index.html                    ← メイン画面
│   │   ├── style.css                     ← スタイル
│   │   ├── app.js                        ← ロジック
│   │   └── ...                           ← その他ソースコード
│   │
│   ├── demo/                             ← 🖥️ デモ確認ページ
│   │   └── index.html                    ← ブラウザで開く → 進捗・プレビュー表示
│   │
│   ├── business/                         ← 🏢 ビジネスサイドの領域
│   │   ├── 要件・方針.md                 ← やりたいこと・ゴール・優先順位
│   │   ├── フィードバック.md             ← コード・進捗へのレスポンス
│   │   ├── 意思決定ログ.md               ← 決定事項の記録
│   │   └── コード改善案/                 ← ✨ Cursorで作った改善コード
│   │       └── YYYYMMDD_改善内容.html
│   │
│   ├── engineering/                      ← 💻 エンジニアの領域
│   │   ├── 技術設計.md                   ← 技術仕様・アーキテクチャ
│   │   ├── 進捗報告.md                   ← 実装状況の報告
│   │   └── 質問・相談.md                 ← ビジネスへの確認事項
│   │
│   └── shared/                           ← 🤝 共有エリア
│       ├── 議事録/
│       └── 参考資料/
```

### 領域の役割分担

| 領域 | 誰が書く | 誰が読む | 内容 |
|------|---------|---------|------|
| **`app/`** | エンジニア | 全員 | 実際のプロダクトコード |
| **`demo/`** | エンジニア | ビジネス | ブラウザで確認できるデモ |
| `business/要件・方針.md` | ビジネス | エンジニア | 何をやりたいか |
| `business/フィードバック.md` | ビジネス | エンジニア | コード・進捗へのレスポンス |
| **`business/コード改善案/`** | **ビジネス** | **エンジニア** | **Cursorで作った改善提案コード** |
| `business/意思決定ログ.md` | ビジネス | 全員 | 経営判断の記録 |
| `engineering/技術設計.md` | エンジニア | ビジネス（概要部分） | どう作るか |
| `engineering/進捗報告.md` | エンジニア | ビジネス | 今何が動くか |
| `engineering/質問・相談.md` | エンジニア | ビジネス | 判断が欲しいこと |

## ワークフロー詳細

### 1. プロジェクト開始

```
エンジニア:
  1. テンプレートからプロジェクトフォルダを作成
  2. app/ に最初のプロトタイプを作成
  3. demo/index.html にデモ確認ページを設置
  4. push → 「デモを確認してください」と連絡

ビジネスサイド:
  1. Cursorを開く
  2. demo/index.html をブラウザで開いて確認
  3. business/要件・方針.md に方針を記載
  4. AIに「GitHubに送って」と頼む
```

### 2. 開発サイクル（毎週）

```
エンジニア:
  1. app/ のコードを開発・更新
  2. demo/index.html のデモを最新に更新
  3. engineering/進捗報告.md に実装状況を記載（どの機能が動くか）
  4. push → 「今週のデモ更新しました」と連絡

ビジネスサイド:
  1. 「最新に更新して」→ AIがpull
  2. demo/index.html をブラウザで開いて確認
  3. 良い点・改善点をフィードバック
  4. 必要ならCursorで改善コードを作成
  5. 「GitHubに送って」→ AIがpush
```

### 3. コード改善案を作る時

```
ビジネスサイド:
  1. app/ の現在のコードをAIと一緒に確認
  2. 「この色を変えたい」「ここにグラフを追加したい」等の要望を伝える
  3. AIが business/コード改善案/ にサンプルコードを作成
  4. ブラウザで確認して「これでOK」
  5. 「エンジニアに送って」→ push

エンジニア:
  1. business/コード改善案/ の新しいファイルを確認
  2. ブラウザで開いてBefore/Afterを比較
  3. 採用する場合は app/ に反映
  4. engineering/進捗報告.md に「改善案を反映しました」と記載
```

### 4. 意思決定が必要な時

```
エンジニア:
  engineering/質問・相談.md に質問を追記
  → 「AかBか、どちらの方針で進めますか？」

ビジネスサイド:
  AIに「エンジニアからの質問を見せて」と聞く
  → business/フィードバック.md に回答
  → business/意思決定ログ.md に決定事項を記録
```

## ビジネスサイドがCursorのAIに言うフレーズ集

### デモ・コード確認系

```
「デモを見たい。どこを開けばいい？」
「今どの機能が動いてるの？」
「前回から何が変わった？」
「このコードは何をしてるの？」（ファイルを開いた状態で）
```

### テキストフィードバック系

```
「○○プロジェクトにフィードバックを書きたい」
「この画面の色をもっと温かみのある感じにしたい」
「ボタンの位置を変えてほしいと伝えて」
```

### コード改善案を作る系

```
「この画面のボタンの色を変えた改善案を作りたい」
「ここにグラフを追加したサンプルを作って」
「この文言を変更した版を作ってほしい」
「Before/Afterで比較できるようにして」
```

### 送信・更新系

```
「これをGitHubに送って」
「最新の状態に更新して」
「今の変更を保存してエンジニアに送って」
```

## Git運用ルール

### コミットメッセージ規約

```
[biz] プロジェクト名: テキストフィードバック等
[biz-code] プロジェクト名: コード改善案の提出
[eng] プロジェクト名: コード実装・修正
[shared] プロジェクト名: 共有ドキュメント
```

例：
```
[biz] ポイント経済圏: UIデザインへのフィードバックを追記
[biz-code] ポイント経済圏: ボタンカラーの改善案を追加
[eng] ポイント経済圏: ポイント残高表示の実装
[eng] ポイント経済圏: ビジネスのカラー改善案を本番コードに反映
```

## 成功のための4つのポイント

### 1. デモが共通言語

仕様書のテキストではなく、`demo/index.html` で見える「動くもの」が共通言語。
「この画面のこの部分」と具体的に指差して議論できる。

### 2. ビジネスサイドもコードで提案できる

テキストだけのフィードバックは解釈のずれが起きやすい。
CursorのAIを使えば、ビジネスサイドも「こういうイメージ」をコードで表現できる。
エンジニアは「言葉」ではなく「動くもの」を受け取れる。

### 3. エンジニアは本番コードに集中

ビジネスサイドの改善案は `business/コード改善案/` に入る。
エンジニアは `app/` の本番コードだけに責任を持ち、
改善案を参考にしながら品質を担保して反映する。

### 4. 全部がリポジトリに残る

コード、デモ、フィードバック、改善案、意思決定、すべてがGitHubに記録される。
「あの時なぜこの仕様にしたんだっけ？」が全部辿れる。
