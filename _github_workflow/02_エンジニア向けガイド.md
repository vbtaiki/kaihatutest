# エンジニア向け GitHub協働ワークフロー ガイド

> ビジネスサイドがCursorから送ってくる情報を活用し、プロジェクトを推進するためのガイド

---

## 概要

このワークフローでは、ビジネスサイド（経営・企画等）の人たちがCursor + AIを使って
GitHubリポジトリにフィードバックや方針を記録します。

エンジニアは通常のGitHub開発フローで開発を進めつつ、
ビジネスサイドの更新を確認してプロジェクトを推進します。

---

## エンジニアの責任範囲

### 1. 初期セットアップ

- [ ] GitHubプライベートリポジトリの作成
- [ ] ビジネスメンバーのGitHubアカウント招待
- [ ] ビジネスメンバーのPCでのクローン・SSH設定
- [ ] Cursorの初期設定確認

### 2. プロジェクト作成時

- [ ] テンプレートからプロジェクトフォルダを作成
- [ ] README.mdにプロジェクト概要を記載
- [ ] `engineering/質問・相談.md` に初回の確認事項を記載
- [ ] ビジネスサイドに確認を依頼

### 3. 開発サイクル中

- [ ] `app/` のコードを開発・更新
- [ ] `demo/index.html` の進捗数値・チェックリストを更新
- [ ] `engineering/進捗報告.md` に週次で進捗を記載
- [ ] 判断が必要な事項を `engineering/質問・相談.md` に記載
- [ ] `business/フィードバック.md` の新しい記載を確認
- [ ] `business/コード改善案/` の新しいファイルを確認（Before/After比較）
- [ ] `business/意思決定ログ.md` の決定事項を確認して開発に反映

## ディレクトリ構造と運用

```
projects/[プロジェクト名]/
├── README.md
├── app/                         ← 🔧 エンジニアが開発するコード
│   ├── index.html               ← メイン画面
│   ├── style.css                ← スタイル
│   └── app.js                   ← ロジック
├── demo/                        ← 🖥️ プロジェクトダッシュボード
│   ├── index.html               ← メインダッシュボード（タブ切替）
│   └── history.html             ← やり取り履歴ページ
├── business/                    ← 🏢 ビジネスサイドが更新する（読むだけ）
│   ├── 要件・方針.md
│   ├── フィードバック.md
│   ├── 意思決定ログ.md
│   └── コード改善案/            ← ✨ ビジネスがCursorで作った改善コード
├── engineering/                 ← 💻 エンジニアが更新する
│   ├── 技術設計.md
│   ├── 進捗報告.md
│   └── 質問・相談.md
└── shared/
    ├── 議事録/
    └── 参考資料/
```

### `app/` — プロダクトコード

エンジニアが開発する本番コード。ビジネスサイドは読むだけ。
ビジネスサイドの改善案は `business/コード改善案/` に入るので、
`app/` を直接編集するのはエンジニアだけ。

### `demo/` — プロジェクトダッシュボード

`demo/index.html` をブラウザで開くと、以下の3タブが表示される統合ダッシュボード：

| タブ | 内容 |
|------|------|
| 💻 エンジニア最新版 | `app/` のプレビュー（iframe） + 開発進捗 + エンジニアからの報告 |
| 💡 ビジネス改善提案 | テキスト指摘 + Before/After比較 + コード差分 |
| 🔄 使い方ガイド | Cursorでのフレーズ集 + ファイル構成図 |

`demo/history.html` には過去のやり取り履歴がタイムライン表示される。

**重要**: `app/` のコードを更新したら、`demo/index.html` の内容（進捗数値・機能チェックリスト等）も合わせて更新すること。

### `business/コード改善案/` — ビジネスからの提案コード

ビジネスサイドがCursorのAIと一緒に作った改善提案コード。
Before/After比較ができるHTMLファイルとして入ってくる。

```bash
# 新しい改善案を確認
ls business/コード改善案/
# → 20260210_ポイントバッジをティールグリーンに変更.html
# ブラウザで開くとBefore/Afterが見れる
```

採用する場合は `app/` に反映し、`engineering/進捗報告.md` に記載する。

### `engineering/進捗報告.md` の書き方

```markdown
## 2026-02-09（日）

### 今週の進捗
- API設計のドラフトを完了
- データベーススキーマを確定
- フロントエンドのワイヤーフレームを作成

### 来週の予定
- API実装（認証周り）
- テスト環境のセットアップ

### ブロッカー
- なし

### ビジネスサイドへの共有事項
- 画面デザインの方向性について、参考資料を `shared/参考資料/` に置きました
- 確認お願いします

---
```

### `engineering/質問・相談.md` の書き方

```markdown
## 2026-02-09: ポイント付与ルールについて

**質問**: ポイントの有効期限はどうしますか？
**選択肢**:
- A: 無期限（シンプルだがコスト増）
- B: 1年（一般的だが離脱リスク）
- C: 2年（バランス型）

**エンジニアの推奨**: B（1年）。システム的にも管理しやすい。
**回答期限**: 2026-02-14

---
```

> ビジネスサイドは `business/フィードバック.md` に回答を記載します。

## ブランチ戦略

### 基本ルール

```
main ─────────────────────────── 安定版
  │
  ├── biz/* ──────────────────── ビジネスサイドのpush（Cursorから）
  │   └── main にそのまま入る（Phase 1）
  │
  ├── feat/* ─────────────────── 機能開発
  │   └── PR → レビュー → main
  │
  ├── fix/* ──────────────────── バグ修正
  │   └── PR → レビュー → main
  │
  └── docs/* ─────────────────── ドキュメント更新
      └── PR → レビュー → main
```

### Phase 1（初期運用）

- ビジネスサイドは `main` に直接push
  - Cursorが `git add -A && git commit && git push` を実行
  - ビジネスサイドのファイルは `business/` 配下のみなので影響範囲が限定的
- エンジニアはPR経由

### Phase 2（慣れてきたら）

- ビジネスサイドも `biz/` プレフィックスのブランチを使用
- エンジニアが確認後にマージ
- GitHub Actionsで自動通知

## コミットメッセージ規約

### プレフィックス

| プレフィックス | 用途 | 例 |
|--------------|------|-----|
| `[biz]` | ビジネスサイドの更新（AI自動生成） | `[biz] ポイント経済圏: FBを追記` |
| `[eng]` | エンジニアの開発・ドキュメント | `[eng] SKYPOD: API設計を追加` |
| `[shared]` | 共有ドキュメントの更新 | `[shared] 議事録: 2/9定例会` |
| `[feat]` | 機能実装 | `[feat] ポイント計算ロジック実装` |
| `[fix]` | バグ修正 | `[fix] ポイント計算の丸め誤差修正` |
| `[infra]` | インフラ・環境 | `[infra] CI/CDパイプライン設定` |

### ビジネスサイドの更新を追跡する方法

```bash
# ビジネスサイドの更新だけ見る
git log --oneline --grep="\[biz\]"

# 特定プロジェクトのビジネス更新を見る
git log --oneline --grep="\[biz\] ポイント経済圏"

# 今週のビジネス更新
git log --oneline --grep="\[biz\]" --since="1 week ago"
```

## GitHub Actionsによる自動化（Phase 2以降）

### Slack通知

```yaml
# .github/workflows/notify-business-update.yml
name: Notify Business Update
on:
  push:
    paths:
      - 'projects/**/business/**'
jobs:
  notify:
    runs-on: ubuntu-latest
    steps:
      - name: Notify Slack
        uses: 8398a7/action-slack@v3
        with:
          status: custom
          custom_payload: |
            {
              "text": "📝 ビジネスサイドから更新がありました: ${{ github.event.head_commit.message }}"
            }
```

### 変更サマリー自動生成

```yaml
# .github/workflows/weekly-summary.yml
name: Weekly Summary
on:
  schedule:
    - cron: '0 9 * * 1'  # 毎週月曜 9:00
jobs:
  summary:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Generate Summary
        run: |
          echo "# 週次サマリー $(date +%Y-%m-%d)" > summary.md
          echo "## ビジネスサイドの更新" >> summary.md
          git log --oneline --grep="\[biz\]" --since="1 week ago" >> summary.md
          echo "## エンジニアの更新" >> summary.md
          git log --oneline --grep="\[eng\]" --since="1 week ago" >> summary.md
```

## ビジネスサイドのオンボーディング手順

エンジニアがビジネスサイドのメンバーを最初にセットアップする手順：

### 1. GitHubアカウント作成

```
1. https://github.com にアクセス
2. メールアドレスで登録（無料プランでOK）
3. リポジトリのCollaboratorに招待
```

### 2. PCセットアップ

```bash
# Gitの初期設定（エンジニアが代行）
git config --global user.name "名前"
git config --global user.email "メールアドレス"

# SSH鍵の生成と登録（エンジニアが代行）
ssh-keygen -t ed25519 -C "メールアドレス"
# → 公開鍵をGitHubに登録

# リポジトリのクローン（エンジニアが代行）
cd ~/Desktop
git clone git@github.com:valuebooks/[リポジトリ名].git
```

### 3. Cursorの設定

```
1. Cursorをインストール（https://cursor.sh）
2. File → Open Folder でクローンしたフォルダを開く
3. .cursorrules が自動的に読み込まれる
4. Cmd+L でAIチャットが開くことを確認
5. 「最新の更新を教えて」と話しかけてテスト
```

### 4. 動作確認

```
1. business/フィードバック.md に「テスト」と追記
2. AIに「これをGitHubに送って」と依頼
3. GitHubのWebでコミットが反映されているか確認
4. テストの記載を削除して再度push
```

## 注意事項

### ビジネスサイドのpushで気をつけること

- ビジネスサイドは `business/` 配下のファイルしか編集しない前提
- 万が一他のファイルを変更しても、`git add -A` で全部入るので注意
  - Phase 2では `.gitattributes` や GitHub Actions で制御可能
- コンフリクトが発生した場合、ビジネスサイドのAIが対処を試みるが、
  解決できない場合はエンジニアに連絡が来る想定

### ビジネスサイドのサポート

- 最初の1-2週間は「何かあったらすぐ聞いて」のスタンスで
- SlackにGitHub通知を流し、ビジネスサイドのpushが来たらリアクションを返す
- 「ちゃんと届いてますよ」のフィードバックが大事
