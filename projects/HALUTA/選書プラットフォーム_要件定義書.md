# バリューブックス 選書プラットフォーム 機能追加要件定義書

> **目的**: 既存の「選書AI・ライブラリ・検索」に機能を追加し、HALUTA案件のような法人向け選書業務をサイト内で完結させる。
> 書店・セレクトショップが選書・仕入れに日常的に使えるプラットフォームへ進化させる。

---

## 1. 現状の整理

### 1-1. 既存機能（サイトにすでにあるもの）

| 機能 | 概要 |
|------|------|
| **選書AI** | AIによる書籍レコメンデーション |
| **ライブラリ** | 本のコレクション管理機能 |
| **検索** | 書籍データベースの検索 |
| **在庫DB** | ISBN・価格・コンディション・在庫数を保持 |
| **買取/販売** | 個人向け古本の売買 |

### 1-2. 進行中のプロジェクト（連携対象）

| プロジェクト | 関連度 | 連携ポイント |
|-------------|--------|------------|
| **プロアカウント（バイヤー機能）** | ★★★ | 書店の卸売仕入れ導線と直結。選書→仕入れが一気通貫になる |
| **本棚スキャン** | ★★☆ | クライアント店舗の既存在庫を撮影→自動リスト化→消し込みに使える |
| **ポイント経済圏** | ★☆☆ | 選書リスト経由での購入にポイント還元を連動 |

### 1-3. 今回のHALUTA案件で手作業だった工程

```
① クライアントの世界観を理解する（ブランドリサーチ）
② 選書コンセプトを決める（北欧・家具・建築・暮らし）
③ 過去に選書・納品した本を読み込む（CSVを手動で突合）
④ AIで候補を大量生成する（200冊以上の候補出し）
⑤ 過去納品との重複を除外する（タイトル・ISBN照合）
⑥ ISBN を外部API で検証する（NDL・openBD）
⑦ 誤マッチを目視で修正する
⑧ 最終リストをCSV出力する
```

**→ ①②④ は「選書AI」の拡張、③⑤ は「消し込み」新機能、⑥⑦ は裏側のデータ基盤強化、⑧は既存のエクスポートを拡張すれば対応できる。**

### 機能A：クライアントプロフィール管理

#### なぜ必要か

今回HALUTAの選書では「北欧ヴィンテージ家具の店」「長野県上田市」「暮らしの道具や建築にも関心が高い」といったブランド情報を**毎回口頭で伝えていた**。これを構造化して保存することで、2回目以降の選書が格段に速くなり、担当者が変わっても引き継げる。

#### 機能一覧

| # | 機能 | 詳細 | 優先度 |
|---|------|------|--------|
| A-1 | **クライアント基本情報** | 企業名、業態、所在地、WebサイトURL、Instagram等 | ★★★ |
| A-2 | **ブランドタグ** | 世界観を表すタグを複数設定（例：`#北欧` `#家具` `#暮らし` `#民藝`） | ★★★ |
| A-3 | **コンセプトメモ** | 自由記述のブランド説明文。AIが選書時に参照する | ★★★ |
| A-4 | **ムードボード** | 店舗写真・空間の雰囲気画像をアップロード | ★★☆ |
| A-5 | **担当者メモ** | 「中村好文系の建築本が鉄板」「森百合子の北欧本は全部入れてOK」等の暗黙知 | ★★☆ |
| A-6 | **過去の選書プロジェクト一覧** | このクライアントに対する全選書履歴 | ★★★ |

#### ユーザーストーリー
- 選書担当者が「HALUTA」のプロフィールページを開くと、ブランドタグ・過去の選書・担当者メモが一覧でき、初めての担当者でも世界観を即座に把握できる。

#### データモデル

```

  id: UUID
  name: String              // "HALUTA"
  business_type: String     // "セレクトショップ"
  location: String          // "長野県上田市"
  website_url: String
  brand_tags: String[]      // ["北欧", "家具", "建築", "暮らし", "民藝"]
  concept_note: Text        // AIが参照するブランド説明
  mood_images: File[]
  staff_notes: Text
  created_at: DateTime
  updated_at: DateTime
}
```

### 機能B：納品履歴管理＋自動消し込み

#### なぜ必要か

今回最も時間がかかった工程の一つ。過去のCSV（`ハルタ_20260214210328.csv`等）を手動で読み込み、タイトルとISBNを照合して重複を排除していた。**同じクライアントに2度同じ本を選んでしまう**のを防ぐために、納品履歴のDB管理と自動照合が不可欠。

#### 機能一覧

| # | 機能 | 詳細 | 優先度 |
|---|------|------|--------|
| B-1 | **納品履歴のCSVインポート** | 過去の納品リストをアップロード。カラム自動判定＋手動マッピングUI | ★★★ |
| B-2 | **納品履歴DB** | クライアント×ISBN単位で全納品を記録 | ★★★ |
| B-3 | **自動消し込み** | 選書時に候補リストと納品履歴を自動照合。重複を即座にフラグ表示 | ★★★ |
| B-4 | **照合ロジック** | ISBN完全一致 ＋ タイトル類似度照合（表記ゆれ対応） | ★★★ |
| B-5 | **本棚スキャン連携** | クライアント店舗の棚を撮影→認識結果を「既存在庫」として消し込み対象に | ★★☆ |
| B-6 | **手動追加** | 個別にISBNを入力して「納品済み」に追加 | ★★☆ |

#### CSVインポートのカラムマッピングUI

今回のHALUTA案件では以下の2種類のCSVフォーマットが混在していた：

**フォーマット1**（バリューブックス在庫データ）:
```
ISBN-10, ISBN-13, タイトル, 著者, 出版社, 出版日, 書齢, 定価, 価格（新品）, ...
```

**フォーマット2**（選書リスト）:
```
No., ISBN-13, タイトル, 著者, 出版社, カテゴリ
```

→ アップロード時にカラムを自動判定し、「ISBNはこの列ですか？タイトルはこの列ですか？」とユーザーに確認するUIが必要。

#### 照合ロジックの仕様

```
照合優先順位:
1. ISBN-13 完全一致 → 確実に重複
2. ISBN-10→13 変換後一致 → 確実に重複
3. タイトル正規化後の完全一致 → ほぼ確実に重複
4. タイトル先頭8文字一致 ＋ 著者名一致 → 重複の可能性高（警告表示）

正規化ルール:
- 全角/半角統一
- スペース・記号除去（・、：、（）、「」、『』等）
- 副題（サブタイトル）を除去
- ひらがな→カタカナ統一
```

#### ユーザーストーリー
- 選書担当者がHALUTAの新規100冊リストを生成すると、過去に納品した300冊との照合が自動実行され、「この本は2025年10月に納品済みです」とリスト上で即座に警告が出る。

### 機能C：選書コンセプト設計（選書AIの拡張）

既存の選書AIは「この本が好きな人にはこの本もおすすめ」的なレコメンドが中心と思われる。今回のHALUTA案件で必要だったのは、**ブランドの世界観を入力として、テーマ×カテゴリの構成比を設計し、100冊単位で一括生成する**機能。個人向けレコメンドとは異質の「法人向け一括選書」。

### 機能D：AI一括選書エンジン（バックエンド）

#### なぜ必要か

今回のHALUTA案件では、Pythonスクリプトで候補250冊を生成→NDL APIでISBN検証→openBDで二重検証→100冊に絞り込む、という工程を**3回以上の試行錯誤**を経て完成させた。AI候補の3〜4割はISBNが見つからない現実を踏まえ、十分な冗長性を持った内部ロジックが必要。

#### 処理フロー

```
[コンセプト＋カテゴリ構成比＋リファレンス本＋除外リスト]
       │
       ▼
① AI候補生成（目標冊数 × 2.5倍）
   └→ LLM がコンセプトに合う書籍タイトル＋著者を生成
       │
       ▼
② 書誌データ照合（NDL API）
   └→ タイトル＋著者で検索 → ISBN-13を取得
   └→ タイトル類似度スコアで誤マッチ防止（閾値: 60以上）
   └→ ISBN-10 → ISBN-13 自動変換
       │
       ▼
③ ISBN二重検証（openBD API）
   └→ ISBN存在確認＋書影URL＋出版社情報の補完
       │
       ▼
④ 消し込みフィルタ（機能B）
   └→ 納品履歴DBとの自動照合
   └→ 同一プロジェクト内のISBN重複排除
       │
       ▼
⑤ 在庫照合（バリューブックスDB）
   └→ 在庫あり/なし、価格、コンディションを付与
       │
       ▼
⑥ スコアリング＆ランキング
   └→ コンセプト適合度 × 在庫可用性 × 価格帯
   └→ 上位N冊を候補として提示
       │
       ▼
[候補リスト → 機能Eのリスト編集UIへ]
```

#### NDL API連携の技術仕様（今回の検証結果から）

```
エンドポイント: https://ndlsearch.ndl.go.jp/api/opensearch
パラメータ:
  - title: 書籍タイトル（正規化済み）
  - creator: 著者名（姓のみ）
  - cnt: 20（結果取得件数）
  ※ mediatype=1 は使わない（結果が0件になるケースが多発したため）

レスポンスから抽出:
  - dc:identifier[@xsi:type='dcndl:ISBN'] → ISBN
  - dc:title → APIタイトル（照合用）
  - dc:publisher → 出版社
  - dc:creator → 著者
  - dc:language → 言語（jpn判定用）

ISBN変換:
  - ISBN-10（10桁）→ ISBN-13（978+先頭9桁+チェックディジット再計算）

タイトル照合:
  - 正規化: スペース・記号除去、全角半角統一
  - 完全一致: スコア100
  - 部分一致（4文字以上 ＋ 長さ比35%以上）: スコア85
  - 先頭N文字一致: スコア50+N*4
  - 閾値: 60以上で採用

レート制限: 0.3〜0.4秒間隔
```

#### openBD API連携

```
エンドポイント: https://api.openbd.jp/v1/get?isbn={isbn13}
用途:
  - ISBNの存在確認（NDLの結果を二重検証）
  - 書影URLの取得（summary.cover）
  - 出版社名の補完（summary.publisher）
  - 著者名の正規化（summary.author）
```

### 機能E：選書リスト編集UI

### 機能F：エクスポート＆プロアカウント連携

#### なぜ必要か

今回はCSV出力で完了だったが、本来は「選書→仕入れ発注」まで一気通貫で行きたい。プロアカウントのバイヤー機能と連携すれば、選書リスト確定→ワンクリックで卸売発注が可能になる。

#### 機能一覧

| # | 機能 | 詳細 | 優先度 |
|---|------|------|--------|
| F-1 | **CSV出力** | 現行フォーマット互換（No, ISBN-13, タイトル, 著者, 出版社, カテゴリ） | ★★★ |
| F-2 | **PDF提案書** | 書影付きの見栄えの良い提案書。クライアントに見せる用 | ★★☆ |
| F-3 | **バイヤーカートに一括投入** | 確定リストの在庫あり分をプロアカウントの卸売カートに一括追加 | ★★★ |
| F-4 | **在庫リクエスト連動** | 在庫なしの書籍を出版社への仕入れリクエストとして自動起票 | ★★☆ |
| F-5 | **リスト共有リンク** | クライアントに閲覧専用リンクを共有（書影+タイトル一覧） | ★★☆ |
| F-6 | **納品記録の自動書き込み** | 発注完了→納品履歴DB（機能B）に自動登録。次回の消し込みに反映 | ★★★ |

#### 選書→仕入れの一気通貫フロー

```
選書リスト確定
    │
    ├─── VB在庫あり（80冊）──→ バイヤーカートに一括投入 → 発注
    │
    └─── VB在庫なし（20冊）──→ 在庫リクエスト起票
                                  │
                                  ├─ 出版社在庫あり → 仕入れ → 納品
                                  └─ 絶版/入手困難 → 代替提案 or 除外
```

| B-3, B-4 自動消し込み | 1週間 | 重複排除の完全自動化 |
| D（一部）AI一括選書エンジン | 2週間 | NDL+openBD連携をサーバーサイドに実装 |

| E-9 担当者コメント | 3日 | 選書理由の蓄積→ナレッジ化 |
| F-2 PDF提案書 | 1週間 | クライアント向けのプレゼン資料自動生成 |
| F-5 リスト共有リンク | 3日 | クライアントとの確認フロー効率化 |
