## 📊 開発原則の重要ポイント

### 基本方針

```
✅ Buy > Build - SaaSを最大活用
✅ MVP思考 - 最小限で素早くリリース
✅ データドリブン - データで意思決定
✅ スケーラビリティ - 10倍成長に耐える設計
```

### 技術スタック標準

| 領域 | 技術 |
|------|------|
| **フロントエンド** | Next.js 16, Flutter |
| **バックエンド** | Python FastAPI, Go |
| **データベース** | PostgreSQL, Redis |
| **インフラ** | GCP, Docker, Cloud Run |
| **AI/ML** | YOLO, CLIP, LightGBM |

### アーキテクチャ原則

```
✅ マイクロサービス指向
✅ RESTful API設計
✅ レイヤードアーキテクチャ
✅ 疎結合・高凝集
```

## 🚀 推奨ワークフロー

### 新規プロジェクト開始時

```
Step 1: 00_開発原則_全体ルール.md を読む（必須）
    ↓
Step 2: 技術選定（標準スタックから選ぶ）
    ↓
Step 3: アーキテクチャ設計
    ↓
Step 4: プロジェクトシート作成
```

### 開発中

```
毎週:
- PRテンプレートに従ってレビュー
- コーディング規約を確認

毎月:
- 開発原則の見直し
- 新しいベストプラクティスを追加
```

### レビュー時

```
チェックポイント:
✅ 開発原則に準拠しているか
✅ 標準技術スタックを使っているか
✅ セキュリティ基準を満たしているか
✅ テストが書かれているか
```

## 🆘 よくある質問

### Q1. 標準スタック以外を使いたい場合は？

**A:** 
1. リードエンジニアに相談
2. メリット・デメリットを整理
3. チーム会議で承認
4. 開発原則に追記

### Q2. 開発原則と違うコードを見つけた

**A:**
1. まずは書いた人に確認
2. 理由があれば文書化
3. 理由がなければリファクタリング

### Q3. 技術的に詳しすぎて分からない

**A:**
- まずは「基本方針」だけ理解
- 実装しながら少しずつ学習
- チームメンバーに質問OK
