## 提案の核心：「戦略実行エンジン」を順番に起動する

### 案3でも案3'でもない、**案3''（ダブルダッシュ）**

案3と案3'の議論は「移行のアプローチ」に焦点がある。
本提案は視点を変える：**「どの事業戦略を、いつ、技術的に実行可能にするか」**から逆算する。

```
案3 の問い：  どの機能を、どう作り直すか？
案3' の問い： どの新しい価値を、どう作るか？
案3'' の問い： どの事業戦略を、いつ実行可能にするか？
```

### 案3''の原則

1. **事業戦略の優先順位が、技術の優先順位を決める**
2. **各フェーズが独立した事業価値を持つ**（案3'を継承）
3. **旧システムは動いている限り触らない**（案3'を継承）
4. **新システムの各パーツは、特定の事業戦略を直接加速する**
5. **「移行」は結果として起きる。目的にはしない**

## 事業戦略の優先順位（CTOとしての提案）

### なぜこの順序か

```
         売上インパクト
         ▲
         │
    ⑤プロAcc │           ②新刊販売
    (将来大)  │           (今年の柱)
         │    ①ポイント
         │    (循環の核)
         │
         │  ③SKYPOD    ④本棚スキャン
         │  (コスト効率)  (入口の革新)
         │
         └──────────────────────────→ 実装の容易さ
                                  （技術的な前提条件の少なさ）
```

| 優先度 | 戦略 | 理由 |
|--------|------|------|
| **★1** | ② 新刊販売 + ダム戦略 | **今期の売上成長の柱。** 仕入れシステムが未構築。既存BQデータで即効性あり |
| **★2** | ① ポイント経済 | **循環エコシステムの核。** 新刊販売と組み合わせて初めて威力が出る |
| **★3** | ④ 本棚スキャン → プロダクト化 | **買取の入口革新。** 技術は98.5%完成。プロダクト化のラストマイルが必要 |
| **★4** | ③ SKYPOD連携 | **倉庫のAPI化。** ハードウェア導入のタイムラインに合わせる |
| **★5** | ⑤ プロアカウント | **エコシステム拡張。** 書誌API + 在庫APIが動いてから |
| **★6** | ⑥ メディア × コマース | **コンテンツ導線。** フロントエンドリニューアルと同時 |

## 技術ロードマップ：6つのフェーズ

### Phase 0：基盤整備 + 新刊仕入れシステム（3月〜4月、6週間）

**事業戦略との関連：② 新刊販売、ダム戦略**

- BQに必要データはすべて揃っている（kaitori_master_bi、hassou_master、m_genpin）
- 旧システムに一切手を入れず構築可能
- **月次の仕入れ判断を自動化するだけで、粗利率が22%→30%以上に改善**（直接取引60%移行時）

**作るもの：**


## チーム体制

### 現実的な提案：3名の即時採用 + AI最大活用

**第1位：テックリード / アーキテクト（正社員）**
- Phase 0〜5 の全体設計責任
- API設計、DB設計、技術選定の意思決定者
- 後から入るメンバーの「土台」を作る人

**第2位：SRE / DevOps（正社員 or 長期業務委託）**
- CI/CD構築、テスト自動化、監視基盤
- この人がいないと「AIがコードを書く」ワークフローが成立しない
- GitHub Actions + Cloud Run + Cloud SQL の運用

**第3位：データエンジニア（業務委託→正社員化）**
- BQ→新DBのETLパイプライン構築
- Phase 0の仕入れインテリジェンスの実装者
- 既存データの型変換・正規化（全部STRING問題の解消）

### AI活用のワークフロー

```
要件（人が定義）
  → 仕様書（AIが生成、人がレビュー）
    → コード（AIが生成）
      → テスト（AIが生成）
        → CI/CD（自動実行、品質ゲート）
          → デプロイ（人が承認）
```

**技術選定で最も大事なこと：「AIが書きやすい」を最優先。**
- Go or TypeScript（学習データ豊富、型あり）
- PostgreSQL（実績豊富、JSONBで柔軟）
- Next.js（SSR + SEO、AIが最も得意なFW）
- GitHub Actions（AI PRも人のPRも同じパイプライン）

## CTOとして最も大事にすること

### 1. 事業の邪魔をしない
旧システムは動いている限りそのまま動かす。技術のリファクタリングに夢中になって売上を止めない。

### 2. 売上に直結するものから作る
Phase 0で仕入れシステムを最初に作るのは、それが**今日の売上**に直結するから。技術者のための技術ではなく、事業のための技術。

### 3. 小さく始めて、早く見せる
6ヶ月計画を立てて6ヶ月後に「できました」ではなく、2週間で動くものを見せてフィードバックをもらう。仕入れダッシュボードは2〜3週間で動くものが作れる。

### 4. データで議論する
「この機能は必要だと思う」ではなく「この機能を使っているのは月間○○人で、売上貢献は○○円」で話す。BQにデータがある。使い倒す。

### 5. IPOストーリーを意識する
各フェーズの成果物は、IPO時の成長ストーリーの材料になる。「書誌インテリジェンスAPI」「本の価値データベース」「プロアカウントプラットフォーム」— これらは投資家に語れるプロダクト。

### 6. 「本が好きな人」のためのプロダクトを作る
Amazonが効率で勝つなら、バリューブックスは**愛着**で勝つ。技術は手段。目的は「本の循環を加速し、読者と本の出会いを最大化する」こと。
