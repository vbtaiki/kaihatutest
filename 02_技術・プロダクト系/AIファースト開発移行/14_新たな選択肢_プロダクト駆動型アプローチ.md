**既存3案とは異なる第4の選択肢。「何を作り替えるか」ではなく「何を作るか」から始める**
**作成日: 2026-02-28**

## 既存3案の共通の前提を問い直す

### 3案はすべて「置き換え」の計画である

| 案 | 問い | 答え |
|---|---|---|
| 案1 | 今のシステムのまま何ができるか？ | AI活用を既存の上に載せる |
| 案2 | どの順序で置き換えるか？ | 業務単位で段階的に |
| 案3 | どの機能を残して作り直すか？ | Sランクから再構築 |

3案すべてが **「既存機能の再現」をゴールの基本線** に置いている。
仕分けシートのS/A/B/C/Dも、「今ある機能のうちどれを残すか」の判定。

これは正しいアプローチだが、見落としていることがある。

### 見落とし：「まだ作っていないもの」の中にこそ武器がある

BQ実地調査（13_BQデータと新システム構想の整合性分析.md）で判明した事実：

| 発見 | 数字 | 意味 |
|---|---|---|
| m_shoshi の in_source = 100% Amazon | 350万件すべて | **現行は書誌データの入口がAmazon一択** |
| m_shoshi_nippan カバレッジ 99.3% | 348万/350万件 | **日販データは揃っているのに使われていない** |
| m_genpin | 4,112万件 | **状態別価格の履歴は日本最大級の古本価値データ** |
| shelf_items（ライブラリ） | テーブル存在確認済み | **読書行動データの種がある** |
| ポイントテーブル | 存在しない | **循環エコシステムの中核がまだない** |

つまり：
- **持っているのに活かせていないデータ**（nippan、genpin の価値データ）
- **種はあるのに育てていないプロダクト**（ライブラリ、選書AI）
- **戦略の中核なのにまだ存在しないもの**（ポイント、プロアカウント）

これらは **「移行」では生まれない。新しく作る必要がある。**
そして、これらこそが **Amazonとの差別化要素** になる。

## Amazonが構造的に持てないもの

Amazonに品揃え・物流スピード・価格で勝つのは不可能。
しかし、Amazonの構造上 **持てないデータと体験** がある。

### 1. 本の循環データ

```
Amazon が見えるもの:
  [出版] → [販売] → [レビュー]

ValueBooks が見えるもの:
  [出版] → [販売] → [読書] → [買取] → [査定] → [再販売] → [次の読者]
                      ↑                                        │
                      └────────────────────────────────────────┘
                                  循環
```

VBだけが **「買う → 読む → 売る → 次の人が買う」** のサイクル全体を持っている。
この循環データは以下を可能にする：

| データ | 可能になること | Amazonにできるか |
|---|---|---|
| 買取価格の時系列（kaitori × satei） | 「この本、3ヶ月後にいくらで売れるか」の予測 | ❌ 買取をしていない |
| 状態別在庫（m_genpin 4,112万件） | 「良品のみ」「書き込みOK」等の条件別価格 | ❌ 新品販売が中心 |
| 読書→売却のタイミング | 「読了後に売る人」vs「積読して売る人」の行動パターン | ❌ 売却データを持たない |
| 買取→再購入のサイクル | リピーターの「読書ペース」と「ジャンル遷移」 | ❌ 循環の片側しか見えない |

### 2. キュレーション体験

Amazonの商品ページは **「買う判断を助ける場所」** であり **「出会う場所」** ではない。
検索して、比較して、レビューを読んで、買う。効率的だが、味気ない。

VBが持てる体験：
- 選書AI（既にある）を軸にした **「あなたのための本」** の提案
- ライブラリ（shelf_items）を軸にした **「あの人が読んでいる本」** の発見
- 買取データを軸にした **「今みんなが手放している本」「逆に手放さない本」** のトレンド

### 3. サステナビリティの実感

「古本を買う＝エコ」は概念としては伝わるが、体験としては弱い。
循環データがあれば **「あなたが売ったこの本は、3人目の読者に届きました」** が言える。
これはAmazonには絶対にできない。

## 案3'：プロダクト駆動型アプローチ

### 基本思想

```
案3（現行）：
  旧システムの機能を仕分け → Sランクから再構築 → 新機能は後から追加

  [仕分け] → [設計] → [構築] → [移行] → [新機能]

  ※ 新機能が使えるようになるのは全工程の後

案3'（プロダクト駆動）：
  Amazonにない価値を先に作る → それが新システムの核になる → 旧機能を引き寄せる

  [新しい価値] → [核となるサービス] → [旧機能を統合] → [旧システム縮退]

  ※ 最初から新しい価値が動いている
```

### 案3と案3'の違い

| 観点 | 案3（フルスクラッチ） | 案3'（プロダクト駆動） |
|---|---|---|
| **最初に作るもの** | 書誌DB + 販売 + 買取（既存機能のSランク） | 書誌インテリジェンスAPI + 本の価値データベース |
| **成功の定義** | 旧システムと同等以上の機能が動く | ユーザーが新しい体験をしている |
| **移行の方法** | ビッグバン（新旧切り替え） | ストラングラーフィグ（新が旧を徐々に置き換え） |
| **価値が出るタイミング** | 全工程完了後（数ヶ月〜1年） | Phase 0完了時点（2〜4週間） |
| **失敗した場合** | 旧システムに戻る（工数がすべて無駄） | 各フェーズが独立して価値を持つ |
| **チームのモチベーション** | 「作り直し」なので達成感が出にくい | 「新しいものを作っている」実感がある |
| **BQパイプラインへの影響** | 二重ソース問題が発生（懸念4） | 旧システムは動いたまま。新サービスが横に立つ |

### 最大の違い：「移行期間」が存在しない

案3の最大のリスクは **「新旧並行運用期間」** だった（13_整合性分析の懸念3, 4）。

案3'では **旧システムを止めない。** 新しいサービスを旧システムの横に置き、
旧システムの機能を一つずつ新サービスに移していく。
「移行」ではなく「成長による置き換え」。

## 具体的なフェーズ

### Phase 0：書誌インテリジェンスAPI（2〜4週間）

**作るもの：** m_shoshi + m_shoshi_nippan + m_shoshi_amazon を統合した書誌API

**なぜこれが最初か：**
- データは99.3%揃っている（BQ調査で確認済み）
- 旧システムに一切手を入れずに構築できる
- 片山さんの「3月半ばまでの実証実験」の最適な対象
- 成功すれば全チームが新システムの価値を実感する
- 失敗しても旧システムは無傷

**技術構成：**
```
BQ（valuebooks_db）
  → ETLバッチ（日次）
    → PostgreSQL（新・書誌DB）
      → REST API / GraphQL

新・書誌DB のスキーマ:
  books:
    - id (= vs_catalog_id, 99.3%カバー)
    - isbn, ean, jan
    - title, title_kana         ← m_shoshi_nippan
    - author, author_kana       ← m_shoshi_nippan (構造化済み)
    - publisher, publisher_id   ← m_shoshi_nippan
    - series                    ← m_shoshi_nippan (唯一のソース)
    - cover_image_url           ← m_shoshi_amazon (唯一のソース)
    - publication_date          ← m_shoshi_nippan
    - price                     ← m_shoshi_nippan
    - pages, language
    - category, productgroup    ← m_shoshi
    - is_out_of_print           ← m_shoshi_nippan
    - description               ← 外部API (OpenBD等) で補完
    - created_at, updated_at
```

**この時点で使えること：**
- ISBNを入れると著者・出版社・シリーズ等が構造化されて返る
- 旧システムの書誌参照を段階的にこのAPIに切り替え可能
- 選書AIの精度向上（nippanの著者・シリーズ情報が使える）

### Phase 1：本の価値データベース（Phase 0 + 4〜6週間）

**作るもの：** 書誌API + 価格インテリジェンス

**なぜこれか：**
- m_genpin（4,112万件）× satei_meisai × kaitori の組み合わせは **VBだけが持つデータ**
- 「この本、今いくら？」に即答できるサービスは日本に存在しない
- 出版社・書店・図書館にも提供できるプラットフォームの種

**追加スキーマ：**
```
book_valuations:
  - book_id (FK → books)
  - condition_code
  - current_buy_price       ← kaitori + satei から算出
  - current_sell_price      ← m_genpin の実勢価格
  - price_trend             ← 過去の価格推移から算出
  - demand_score            ← 注文頻度から算出
  - supply_score            ← 買取頻度から算出
  - updated_at
```

**この時点で使えること：**
- 買取価格の即時回答（現在は査定に時間がかかる）
- 「値段が上がっている本」「今が売り時の本」のサジェスト
- 出版社向け：「あなたの本の古本市場での評価」レポート

### Phase 2：読書プラットフォーム（Phase 1 + 6〜8週間）

**作るもの：** ライブラリ機能の拡張 + コミュニティ

**なぜこれか：**
- shelf_items テーブルは既にある（BQ確認済み）
- 日本に「Goodreads相当」のサービスがない空白がある
- ここが **「買う場所」から「出会う場所」への転換点**
- 読書データ × 書誌インテリジェンス × 価値データ = 最強のレコメンデーション

**この時点で使えること：**
- 「あなたの本棚の価値は○○円です」（ライブラリ × 価値データ）
- 「この本を読んだ人は次にこれを読んでいます」（循環データ活用）
- 「今月のトレンド：みんなが手放さない本 TOP 50」

### Phase 3：旧機能の統合（Phase 2 + 並行して進行）

**ここで初めて「移行」が始まる。** だが、この時点で：
- 書誌APIは本番稼働中（旧システムも参照している）
- 価値データベースは業務に使われている
- 読書プラットフォームにユーザーがいる

旧システムの機能を新システムに引き寄せる：
1. VB直販の注文フロー（order_head_vb: 61.9万件、48カラム → 新注文API）
2. 買取フロー（kaitori群 → 新買取API）
3. 顧客管理（customer_master: 77万件 → 新ユーザーDB）

この段階では、案3の仕分けシート（07_機能仕分けシート.md）の S/A ランクが対象。
違いは、 **「空のシステムに機能を足す」のではなく「動いているプロダクトに機能を統合する」** こと。

## この順序にする理由

### 1. 「作り直し」ではなく「新しいものを作っている」

フルスクラッチの最大の心理的障壁は **「今と同じものを作り直す」退屈さ** 。
エンジニアも、経営者も、ユーザーも、「前と同じもの」にワクワクしない。

案3'では最初から **「今までなかったもの」** を作る。
書誌インテリジェンスAPI、本の価値データベース、読書プラットフォーム——
これらはすべて **現行システムに存在しない新しい価値。**

### 2. 各フェーズが独立して価値を持つ

案3は全工程が完了するまで「移行中」。途中で止めると中途半端な状態が残る。

案3'は各フェーズを止めてもそこまでの成果物が残る：
- Phase 0 で止めても → 書誌APIが社内で使える
- Phase 1 で止めても → 価値データベースが業務改善に使える
- Phase 2 で止めても → 読書プラットフォームがユーザーに価値を提供している

### 3. BQパイプラインの問題が消える

案3の最大の技術的懸念は「二重ソース問題」（13_整合性分析 懸念3, 4）だった。

案3'では：
- Phase 0〜2 の間、旧システムは **そのまま動き続ける**
- BQパイプラインも **変更不要**
- 新サービスは旧DBを **読み取るだけ**（BQ経由 or 旧DB参照）
- Phase 3 で初めて書き込み先が変わるが、その時点で新システムは十分に成熟している

### 4. 「Amazon脱却」が自然に起きる

現行: in_source = 100% Amazon（BQ調査で確認済み）

案3のアプローチ: 「Amazonの仕組みをやめて、自社の仕組みに変える」→ 能動的な切り替え
案3'のアプローチ: 「nippanベースの書誌APIが良すぎて、Amazonのデータを参照する理由がなくなる」→ 自然な淘汰

99.3%がnippanデータと紐付いている以上、書誌APIが動き始めた時点で
**Amazon MWSへの依存は自動的に消えていく。**

## リスクと正直な懸念

| リスク | 深刻度 | 対策 |
|---|---|---|
| 「新しい体験」がユーザーに受け入れられない | 中 | Phase 0 は社内向けAPI。ユーザー向けはPhase 2 から。段階的に検証できる |
| Phase 0〜2 に注力している間、旧システムの問題が悪化する | 中 | 旧システムの致命的バグ修正は並行して行う。ただし機能追加はしない |
| 「新しいもの」と「旧機能の移行」の二兎を追う形になる | 高 | **Phase 3 に入るまで旧機能の移行はしない**というルールを厳守する |
| エンジニアのリソースが分散する | 中 | Phase 0〜1 は少人数（1〜2名）で可能。全員が移行に関わる案3より分散しにくい |
| 案3の仕分け作業（07_機能仕分け）が無駄になる | 低 | 無駄にならない。Phase 3 でそのまま使う。タイミングが後ろにずれるだけ |

### 案3'が適さないケース

- **旧システムが今すぐ止まるリスクがある場合** → 新しいものを作っている場合ではない
- **経営から「○月までに移行完了」と期限が切られている場合** → 案3の方が計画を立てやすい
- **チーム全員が「新しいものより移行を優先すべき」と考えている場合** → 合意なき方針転換は失敗する
