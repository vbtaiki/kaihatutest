# 経営判断：案3（フルスクラッチ）で進める方針

**ビジネスオーナー 中村大樹の意思決定メモ — 2026-02-27**

---

## 結論：案3を選択する

3案の比較を踏まえ、**案3：ビッグバン移行（フルスクラッチ再構築）** で進める。

---

## なぜ案3か

### 1. 今のシステムを全部再現する必要はない

現行システムの機能の中には、**実はそんなに重要でないものや今は使っていないもの**がある。
全機能を移行するのではなく、**本質的に重要な機能のみの再現から始める**。

> しばらく足りない機能に困って、必要に応じて機能を追加する期間があってもいい。

### 2. Amazon中心のアーキテクチャを根本から見直す

バリューブックスはAmazon販売からスタートし、後から自社販売が始まった。
そのため**Amazonの仕組みがシステムのベース**になっている。

これを抜本的にひっくり返す。

### 3. 新旧の連携リスクを避ける

案2（緩やかな移行）は、新旧システム間のデータ整合性の維持が最大のリスク。
山口さんの前職でも案2を取って撤退した経験がある。
**中途半端な連携を作らず、新しく作り直す方がシンプル。**

## ビジネスオーナーとしてできること

### 機能の仕分け

現行システムの全機能に対して、ビジネスオーナーの立場から **思い切った仕分け** を行う。

| ランク | 意味 | 判断基準 |
|:------:|------|---------|
| **S** | 🔴 絶対必要 | これがないと事業が止まる |
| **A** | 🟠 できたら必要 | なくても回るが、あった方がいい |
| **B** | 🟡 ついでにあれば | 余裕があれば作る |
| **C** | ⚪ なくてもいい | 実はなくても困らない |
| **D** | ❌ 排除したい | むしろ邪魔。ない方がスッキリする |

→ **この仕分けをしたものを要件定義として会議にあげる。**

※ 具体的な仕分けシートは `07_機能仕分けシート.md` を参照

## 進め方のイメージ

```
Phase 0  ビジネスオーナーの機能仕分け（← いまここ）
         ・既存機能の棚卸し
         ・S/A/B/C/D の判定
         ・新アーキテクチャの要件定義
              ↓
Phase 1  会議で方針決定
         ・仕分け結果をエンジニアと議論
         ・実現可能性の確認
         ・優先順位の最終決定
              ↓
Phase 2  最小限のコア機能を構築
         ・書誌DB + 自社販売 + 買取
         ・足りないものは後から足す覚悟
              ↓
Phase 3  モール連携を横に作る
         ・Amazon / 楽天 / Yahoo 等への出品
         ・在庫連動
              ↓
Phase 4  付加機能を段階的に追加
         ・ポイント経済圏
         ・選書AI
         ・新刊仕入れシステム
         ・本棚スキャン連携
         ・プロアカウント（バイヤー機能）
```

## 覚悟していること

1. **しばらく不便になる** — 今ある機能がすべて揃うまで時間がかかる
2. **現場に負荷がかかる** — 手動でカバーする期間が発生する
3. **過渡期の混乱** — 新旧システムの並行期間がある

> だが、中途半端に旧システムを延命するよりも、
> 思い切って「本当に必要なもの」だけで再構築した方が、
> 1年後・3年後の開発スピードは圧倒的に速くなる。
