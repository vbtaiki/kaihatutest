# 移行3案の比較

**システム移行の方向性 — どの案で進めるか**

---

## 3案の概要

```
案1：移行しない             案2：緩やかな移行           案3：ビッグバン移行
┌──────────────┐    ┌──────────────────┐    ┌──────────────────┐
│ 既存システム   │    │ 既存    │ 新規   │    │         新規      │
│ そのまま運用   │    │ システム│システム │    │     フルスクラッチ  │
│              │    │   ↕ API連携 ↕    │    │      全面構築     │
│  + AI活用     │    │ 業務単位で順次移行 │    │   段階的に業務移行  │
└──────────────┘    └──────────────────┘    └──────────────────┘
```

---

## 詳細比較表

| 観点 | 案1：移行しない | 案2：緩やかな移行 | 案3：ビッグバン移行 |
|------|:---:|:---:|:---:|
| **概要** | 既存システムのまま AI活用 | 業務単位で順次スクラッチ再構築 | 全システムをフルスクラッチで横に構築 |
| **リスク（業務影響）** | ⭕ 最小 | 🔶 中程度 | 🔴 大きい |
| **開発速度の改善** | ❌ 限定的 | 🔶 段階的に改善 | ⭕ 最速 |
| **設計の自由度** | ❌ 低い | 🔶 中程度 | ⭕ 最高 |
| **DB変更** | なし | 新旧DB並行運用 | 全面刷新 |
| **AIファースト開発** | ❌ フル活用困難 | ⭕ 新規部分で適用可 | ⭕ 全面適用 |
| **技術的負債** | 増え続ける | 新規部分は解消 | 全面解消 |
| **データ分断の解消** | ❌ 解消困難 | 🔶 段階的に改善 | ⭕ 根本解決 |
| **現場への影響** | ⭕ なし | 🔶 限定的 | 🔴 混乱の可能性 |
| **期間（初期成果）** | 3ヶ月 | 2ヶ月（新刊販売） | 2ヶ月（一部業務） |
| **期間（全体）** | — | 1年〜 | 6ヶ月〜 |

## 案1：移行しない（既存延長）

### やること
- 既存システムをそのまま運用
- AIを調査・コーディングに適用
- 個人のAIスキルをチーム共有
- 暗黙知をAI利用可能なコンテキストに整備

### メリット
- ✅ 現行業務への影響ゼロ
- ✅ リスクが最も低い
- ✅ すぐに始められる

### デメリット
- ❌ AIの効果を最大限活かせるシステム構成ではない
- ❌ 新規機能追加のスピードアップが限定的
- ❌ 技術的負債は増え続ける
- ❌ データの分断問題は解消されない

### スケジュール
```
Month 1-3: 個人AIスキル向上 + ナレッジシェア整備
Month 4〜:  実践（機能追加・メンテナンスでAI活用）
```

### 各メンバーの評価
- **全員**: 案1だけでは不十分との認識
- **中村大樹**: 1年後にAIが進化すれば1のままでも解決する可能性は？ → 読めない

---

## 案2：緩やかな移行（業務単位の段階的再構築）

### やること
- 業務単位（例：新刊販売）で既存システムから切り離し、スクラッチ再構築
- 新システムと旧システムをAPI連携
- 順次、他の業務も移行

### アーキテクチャイメージ
```
┌──────────────────────────────┐
│      旧システム（モノリス）     │
│  ┌──────┐  ┌──────┐         │
│  │既存DB │  │既存DB │         │
│  │ (RDB) │  │(Open  │         │
│  │      │  │Search)│         │
│  └──┬───┘  └──┬───┘         │
└─────┼──────────┼─────────────┘
      │          │
      │  ACL（腐敗防止層）
      │          │
┌─────▼──────────▼─────────────┐
│      新システム               │
│  ┌──────────┐ ┌──────────┐   │
│  │ WMS      │ │インベントリ │   │
│  │(エグゾテック)│ │サービス   │   │
│  └──────────┘ └──────────┘   │
│         新しいDB              │
└──────────────────────────────┘

※ ACL = Anti-Corruption Layer（ファサードパターン）
  新旧システム間のデータ変換・連携を担う層
```

### メリット
- ✅ 影響範囲を限定できる
- ✅ 新規部分はクリーンなAIファースト開発を適用可能
- ✅ 世間的にも現実的な路線
- ✅ 失敗しても被害が限定的

### デメリット・リスク
- ❌ 新旧システム間のデータ整合性の維持が難しい
- ❌ ダブルライト（新旧両方にデータ書き込み）の整合性リスク
- ❌ 旧システムの制約が新システムの設計を制限する可能性
- ❌ 移行先が増えるほど新旧連携の複雑さが増す
- ❌ 在庫の引き当てなど、新旧で競合する可能性

### スケジュール
```
Month 1-3: 要件ヒアリング + AI開発体制整備
           ベースライン計測
Month 2-4: 新刊販売のスクラッチ構築
Month 4末: システムローンチ → 成果判断
Month 5〜: 他の業務スライスを順次移行（一部並列可）
```

### 各メンバーの評価
- **片山秀夫**: 2は現実的だが、既存の制約を引きずる中間物を作ることになる
- **沓掛大吾**: 2のイメージが湧かない。技術的にデータ同期が可能なのか疑問
- **吉田英代**: 技術的には確信と実績がある。ただし業務ルールの潜在的影響が懸念
- **水野佑紀**: 2をやるなら1番難しいところから。簡単なところだけやって後で困るのは避けるべき
- **山口達輝**: 新旧がDBにお互い書き込み合う状況の整合性リスク。前職で案2を取って撤退した経験あり

---

## 案3：ビッグバン移行（全面フルスクラッチ）

### やること
- 全システムをフルスクラッチで横に構築
- 業務の一部を段階的に新システムへ移行
- 最終的に旧システムを廃止

### メリット
- ✅ スピードが最も速い
- ✅ 設計の自由度が最高（制約なし）
- ✅ AIファースト開発を全面適用
- ✅ データの分断問題を根本解決
- ✅ ドメイン設計を完璧にやれる
- ✅ データの新旧連携問題がない（新システムに一本化）

### デメリット・リスク
- ❌ 現場に混乱を招きやすい
- ❌ 半年〜1年、開発リソースが大きく割かれる
- ❌ データの二重管理（移行期間中）
- ❌ 要件定義が必要（業務知識の棚卸し）
- ❌ 業務知識が属人化しているため、要件の洗い出しにリスクがある

### スケジュール
```
Month 1-2: 要件定義・ドメイン設計
           一部業務で成果判断
Month 1-6: フルスクラッチ構築
Month 6〜: 業務を段階的に新システムへ移行
```

### 各メンバーの評価
- **片山秀夫**: 3が望ましいが、まず実証実験が必要。3のつもりで1個作ってみる
- **沓掛大吾**: 3はイメージできる。全部作り直す方が分かりやすい
- **佐原浩太**: 2は属人化した業務知識不足で問題が起きる → 3の方がいい
- **吉田英代**: Webやプロ向け機能はフルスクラッチ（案3寄り）、基幹システムは現行でもOK
- **山口達輝**: 何も知らない状態で考えると案3の方が安定するイメージ

## 吉田さんの「ハイブリッド案」

会議の終盤で提示された考え方：

```
┌─────────────────────────────────────────┐
│  システムの種類に応じてアプローチを変える    │
├─────────────────────────────────────────┤
│                                         │
│  Web・プロ向け機能                        │
│  → 案3寄り（フルスクラッチ × AIファースト） │
│  → デプロイ頻度が高く、機能追加が多い       │
│                                         │
│  基幹システム（バックヤード）               │
│  → 案1〜2（現行ベースでOK）               │
│  → 業務トラフィック安定、機能追加は少ない   │
│                                         │
└─────────────────────────────────────────┘
```

## コスト試算

| 項目 | 月額 | 備考 |
|------|------|------|
| AIツール利用料 | 要算定 | Claude Code、Cursor等 |
| インフラ二重稼働 | 約240万円 | 新旧システム並行期間 |
| シニアエンジニア | 1名分 | 採用進行中 |
| 外部パートナー（JSL） | 継続 | プロ開発で協力中 |

### お金で解決できるか？

| 投資先 | 効果 |
|--------|------|
| AIツール課金の増額 | ⭕ AIの処理速度向上（例：6倍コストで2.5倍速） |
| 人員増加 | 🔶 初動が遅くなる。業務理解のオンボーディングコスト大 |
| 外部エンジニア | 🔶 正解を提示できれば有効。探索的タスクには不向き |

→ **人的リソースの追加は根本的な解決策にはならない**（片山・吉田・佐々木の共通認識）
