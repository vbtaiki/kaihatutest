##### 1-1c. カバレッジ率調査結果（2026-02-28 追加調査）

m_shoshi（書誌マスター）と各サブテーブルの紐付き率を定量的に確認した。

**レコード数:**

| テーブル | レコード数 | 備考 |

| m_shoshi | 3,506,303 | コア書誌テーブル |

| m_shoshi_nippan | 4,762,802 | 日販由来（m_shoshiより多い） |

**カバレッジ率（m_shoshi 基準）:**

| 指標 | 値 | カバレッジ率 |
|------|---:|:---:|
| m_shoshi 総数 | 3,506,303 | — |
| vs_catalog_id 保有（= nippan 紐付き可能） | 3,481,706 | **99.3%** |
| vs_catalog_id ユニーク数 | 3,481,274 | ほぼ1:1 |
| vs_catalog_id 未保有 | 24,597 | 0.7% |

**in_source（データ取得元）の分布:**

| in_source | 件数 | 割合 |
|:---------:|------:|:---:|
| A（Amazon） | 3,506,303 | **100.0%** |

**🔴 極めて重要な発見: m_shoshi の全レコード（350万件）が Amazon 起点（in_source = 'A'）**

これは現行システムが**完全にAmazon依存**であることのデータ上の証拠。
しかし同時に、**99.3%が日販データ（m_shoshi_nippan）とも紐付いている**。

→ **「Amazon脱却」は定量的に実現可能。** 移行の流れは：
1. m_shoshi_nippan を主データソースとし、著者・出版社・シリーズ等を取得（99.3%カバー）
2. m_shoshi_amazon を補完ソースとし、書影URL等のAmazon固有情報を取得
3. 0.7%（約24,600件）の nippan 未紐付きレコードは、Amazon データまたは手動での補完が必要

## 2. 重大な懸念点

### ✅ 懸念1: 解消 — 書誌情報はサブテーブルに十分存在する

**当初の懸念:** m_shoshi本体に著者・出版社がないため、「書誌DB中心」構想の前提が揺らぐ

**調査結果:** `m_shoshi_amazon`（~70カラム）と `m_shoshi_nippan`（~100カラム）に**著者・出版社・書影URL等が十分に存在**することを確認。

**新たな評価:**
- 書誌情報は **3テーブルに分散しているが、データ自体は揃っている**
- 特に `m_shoshi_nippan` は**Amazon非依存の高品質な書誌データ**（著者3名まで構造化、出版社ID付き、カナ読み、シリーズ情報）
- 「Amazon脱却」構想は、`m_shoshi_nippan` を主データソースとすれば実現可能
- 書影URLのみ `m_shoshi_amazon` に依存（代替手段の検討は推奨）
- `description`（書籍概要）のみ既存テーブルに存在しない → 外部API（OpenBD等）が必要

→ **残るアクション**:
1. ~~サブテーブルのカラム調査~~ ✅ 完了
2. 新書誌テーブルへの統合設計（上記「情報源マトリクス」をベースに）
3. ~~`m_shoshi` と `m_shoshi_nippan` のカバレッジ率確認~~ ✅ **完了（99.3%カバレッジ確認）**
4. 書影URLのAmazon依存を許容するか、代替（OpenBD等）を検討

### 🔴 懸念2: 注文テーブルが販路ごとに15+テーブルに分裂（新発見）

**リスク: 注文データの統合が想定以上に複雑**

既存の注文テーブル構造:
```
order_head_vb          order_head_mercari      order_head_rakuten2      order_head_yahoo
order_hikiate_mercari   order_hikiate_rakuma    order_hikiate_rakuten2   order_hikiate_yahoo
order_meisai_vb        order_meisai_mercari     order_meisai_yahoo
order_process_rakuma   order_process_rakuten2   order_process_yahoo
```

→ 同じ「注文」概念が **販路ごとに別テーブル** で管理されている。
→ これは新システム構想（`09_エンジニア向け提案`）で指摘された「密結合」の最も深刻な具体例。

**影響:**
- 新システムでは1つの `orders` テーブルに統合する構想だが、各販路のテーブルのカラム構造が異なる可能性がある
- ただし、新システム構想では**モール連携は旧システムに残す**方針
- つまりこの15+テーブルは**移行対象外**（旧システムで維持）
- VB直販（`order_head_vb`）の構造のみ理解すれば、新システムの注文テーブル設計に着手可能

→ **推奨アクション**:
1. `order_head_vb` と `order_meisai_vb` のカラム構造を調査
2. 新システムの注文テーブル設計に必要な情報を確認
3. モール連携の注文データとの整合性（BQ上での統合集計の方法）を設計

### 🔴 懸念3: BQ分析パイプラインの移行が「Step 2」に後回しされている

**リスク: S ランクの分析データが断絶する期間が発生する**

新システム構想（07_機能仕分け）では、BQ連携はA ランク（Step 2）に分類されている。
しかし、BQ上の **S ランクデータセット** は業務の根幹：

| Sランクデータセット | 主な用途 | 新システム移行で起きること |
|:--:|------|------|
| `external_source` (70テーブル) | マーケティング・買取分析の中心 | **ソースDBが変わるため、全パイプラインの作り直しが必要** |
| `valuebooks_master` (5テーブル) | 販路別売上分析のメインテーブル | **hassou_master の元データが新DB経由に変わる** |
| `valuebooks_db` (80テーブル) | 本番DBミラー。全業務の根幹 | **新DBのミラーに切り替える必要あり** |

**特に深刻な問題:**
- `kaitori_master_bi`（152万行）は、`kaitori`, `customer`, GA4, 広告データなど**複数ソースのJOIN済みテーブル**
- 新システムでDB構造が変わると、このJOINロジックを**ゼロから作り直す必要がある**
- Step 1 で新DBに切り替えた時点で旧DBからのパイプラインが壊れる
- しかしBQ連携はStep 2 → **分析データが取れない空白期間が発生するリスク**

→ **推奨アクション**: BQ連携（少なくとも `valuebooks_db` のミラーリング）は **Step 1 に昇格** すべき。
新DBからBQへのデータ同期パイプラインは、新システムのリリースと同時に稼働させる必要がある。

---

### 🔴 懸念4: 移行期間中の「二重ソース問題」

**リスク: Phase 1〜3 の移行期間中、BQがデータを取得すべきソースが新旧に分裂する**

```
Phase 1 の状態:
  ┌───────────────────────────────────────────────┐
  │  新DB（書誌・顧客・在庫・買取・注文）          │──→ BQはここからデータを取る
  └───────────────────────────────────────────────┘
  ┌───────────────────────────────────────────────┐
  │  旧DB（物流・モール・現品管理）                 │──→ BQはここからもデータを取る
  └───────────────────────────────────────────────┘

  kaitori_master_bi を作るには:
    kaitori → 新DB  ✓
    customer → 新DB  ✓
    hassou_* → 旧DB  ✗（物流はまだ旧DB）
    campaign → ?（どちらのDB？）
```

**`kaitori_master_bi` のようなJOINテーブル** は、新旧両方のDBからデータを引く必要がある。
この「二重ソース」状態でのBQパイプライン設計は非常に複雑になる。

→ **推奨アクション**:
1. Phase 1 開始時に、新DBのデータも旧DB形式でBQに流す**互換パイプライン**を用意する
2. または、Phase 1 完了まで旧DBのBQパイプラインは維持し、新DBへのパイプラインを並行して構築する
3. `kaitori_master_bi` のJOINロジックを、新旧のどちらのソースからも組める設計にする

---

### 🟡 懸念5: hanbai_kbn / site_code のマッピング設計が未定義

**リスク: 販路・サイトの識別体系が新旧で分裂する**

既存の分類体系:
- `hanbai_kbn`: A1(Amazon), R1(楽天), V1(VB直販), C1(メルカリ), M1(ラクマ), Y1(Yahoo)
- `site_code`: MA1(VB), CH1(チャリボン), VA1(Vaboo)

新システム構想では**4社モデル**で分離するが：
- 「本併売（株）」が扱う販路（A1/R1/C1/M1/Y1）のデータは旧DBに残る
- 「プラットフォーム（株）」のV1(VB直販)は新DBに移る
- BQの分析では**全販路を横断して集計**するのが基本

→ **推奨アクション**: 新旧システム間で販路コード・サイトコードの**統一マスタ**を定義する。
BQ上の既存コード体系（hanbai_kbn, site_code）は維持しつつ、新システム側でもマッピングを保持する。

### 🟡 懸念6: 「新DBが唯一の真実」とBQミラーの関係

**リスク: SSOT原則とBQの役割の整理が不十分**

現在の構造:
```
本番DB → BQ（valuebooks_db）= 本番のミラー
       → BQ（external_source）= 加工済み分析データ
       → BQ（valuebooks_master）= 売上分析データ
```

新システム構想:
```
新DB = SSOT
旧DB = キャッシュ扱い

では BQ は？
  → 新DBのミラー？
  → 新DB + 旧DB の統合ビュー？
  → 独立した分析レイヤー？
```

BQの位置づけが明確でない。以下を整理する必要がある：

| 質問 | 影響 |
|------|------|
| 新DBの全テーブルをBQにミラーするのか？ | パイプライン設計、コスト |
| 旧DBのBQミラー（`valuebooks_db`）はいつ停止するのか？ | Phase完了後も分析に必要? |
| `external_source` の加工済みテーブルは新システムのどこで再現するか？ | BQ内で再構築? 新システムのAPIで提供? |
| `kaitori_master_bi` 相当のデータは新システムが生成するのか？ | 分析ロジックの帰属先 |

### 🟡 懸念7: S3経由のデータパイプライン（vb_production_from_s3）

**リスク: データが3経路でBQに流入し、整合性が取れなくなる**

現在でも2経路が重複:
1. `valuebooks_db` — 本番DBの直接ミラー（100+テーブル）
2. `vb_production_from_s3` — S3経由の本番データ（120テーブル）

新システム導入で3経路目が追加:
3. 新DB → BQ（新パイプライン）

→ **推奨アクション**: Phase 1 開始前に、`valuebooks_db` と `vb_production_from_s3` の重複を解消する。
どちらが「正」かを確定し、片方を停止してからでないと、新パイプライン追加時に混乱が深刻化する。

### 🟡 懸念8: Vaboo閉鎖に伴うデータ処理

**リスク: 分析の連続性が失われる**

Vaboo（site_code = VA1）関連:
- `kaitori` テーブルに VA1 の買取データが混在
- `kaitori_master_bi` にも VA1 データが含まれる
- GA4（`ga4_va_latest`）は Vaboo のもの → 停止予定

Vaboo閉鎖時にデータ面で必要なこと:
1. 歴史的な VA1 データの保存方針（BQにアーカイブ? 新DBに移行?）
2. `kaitori_master_bi` で VA1 を除外するフィルタの追加タイミング
3. 新システムの `site_code` マスタから VA1 を「閉鎖済み」にする

→ これ自体は大きな問題ではないが、**移行計画にVaboo閉鎖の手順を明示的に組み込むべき。**

### 🟡 懸念9: 全データがSTRING型で格納されている（新発見）

**リスク: データ型変換・バリデーションの工数が過小評価される**

BQ調査で判明した事実:
- `sell_price`（販売価格）= STRING "385"
- `teika`（定価）= STRING "0"
- `hatsubai`（発売日）= STRING "2008-12-12"
- `flg_enable`（有効フラグ）= STRING "0"

新システムのPostgreSQLでは当然これらは `INTEGER`, `DATE`, `BOOLEAN` 等の適切な型で定義される。
**300万件以上のデータに対する型変換とバリデーション**（不正値の検出・修正）が必要。

→ **推奨アクション**: 移行スクリプトの工数見積りに「データクレンジング」フェーズを含める。

## 6. 総合評価

### 計画は妥当か？

**方向性は妥当。BQ実地調査により、一部の懸念が解消され、新たな重要課題が判明した。**

#### ✅ 当初懸念が解消された点

- **`m_genpin` は14カラムのシンプルな構造** → Phase 2 のリスクは当初想定より低い
- **ポイントテーブルは存在しない** → 新規構築のため、レガシーとの整合性を気にせず設計できる
- **ライブラリ機能のデータ（`shelf_items`）が存在** → 移行基盤がある

#### ✅ 追加調査で解消された課題

1. **書誌情報の情報源問題 → 解消**
   - `m_shoshi_nippan`（~100カラム）に著者・出版社・シリーズ等が**構造化されて存在**
   - `m_shoshi_amazon`（~70カラム）に書影URL・定価等が存在
   - **「Amazon脱却」は `m_shoshi_nippan` を主データソースとすれば実現可能**
   - 書影URLのみAmazon依存が残る（代替検討推奨）
   - `description`（書籍概要）のみ外部APIが必要

#### ⚠️ 残る重要課題

1. **書誌データの統合設計**
   - 3テーブル（m_shoshi + amazon + nippan）からの統合ロジック設計が必要
   - ✅ m_shoshi_nippan のカバレッジ率 = **99.3%**（確認済み）
   - ✅ in_source = 'A'（Amazon）が **100%** → 現行は完全Amazon依存だが、nippanへの移行基盤あり
   - 残: nippan 未紐付き 0.7%（約24,600件）の補完戦略を決定する必要あり

2. **注文テーブルの販路別分裂**
   - 15+テーブルに分裂した注文データは密結合の象徴
   - ただしモール連携を旧に残す方針であれば、VB直販分のみ新設計で対応可能

3. **全データがSTRING型**
   - 型変換・バリデーションの工数を移行計画に織り込む必要あり

#### 引き続き有効な懸念

- BQ分析パイプラインの移行がStep 2では遅い（→ Step 1に昇格推奨）
- 二重ソース問題への対策が不十分
- BQの位置づけ（SSOT vs 分析レイヤー）の明確化が必要

### 一言でまとめると

> **「新システムの設計方向は正しく、追い風が多い。**
> **書誌情報は m_shoshi_nippan（日販）に構造化されて存在し、カバレッジ率99.3%で「Amazon脱却」の基盤が定量的に確認された。**
> **現行は in_source=100% Amazon だが、350万件中348万件が日販データと紐付いており、主データソースの転換は現実的。**
> **m_genpin の単純さ（14カラム）やポイントテーブルの不在も追い風。**
> **残る課題は、3テーブルからの書誌統合設計、BQパイプラインのStep 1昇格、STRING型データの変換計画。**
> **計画の実現可能性は、当初評価より高いと判断する。」**
