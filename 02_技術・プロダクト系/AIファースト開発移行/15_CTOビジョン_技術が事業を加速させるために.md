# CTOビジョン：技術が事業を加速させるために

**バリューブックスの全資料を読み込んだ上での、技術責任者としての見解**
**作成日: 2026-02-28**

---

## バリューブックスを理解した上での現状認識

### この会社の本質

バリューブックスは「古本屋」ではない。
**本の循環インフラ** であり、その循環の中で生まれるデータを持つ **唯一の企業** 。

```
出版社 → 書店 → 読者 → 買取 → 査定 → 在庫 → 再販売 → 次の読者
                        ↑                                    │
                        └────────────────────────────────────┘
```

Amazonはこの流れの「→ 書店 → 読者」しか見えない。
楽天もメルカリも同じ。
**バリューブックスだけが、この循環の全体を見ている。**

13年間、350万冊の書誌、4,112万件の現品データ、77万人の顧客データ。
これらは時間をかけなければ作れない。技術で複製できない。金で買えない。

### 今の経営が見えている世界

中村さんの戦略は明快：

| 戦略 | 一言で言うと |
|------|-------------|
| ① ポイント循環経済 | 現金を出さず、エコシステム内で回す |
| ② グッズコラボ | B Corp仲間と新しい商材を作る |
| ③ SKYPOD | 倉庫を自動化し、人を解放する |
| ④ 本棚スキャン | 買取の入口をスマートにする |
| ⑤ プロアカウント | 著者・出版社・書店を仲間にする |
| ⑥ メディア拡張 | 積読チャンネルを起点にファンを作る |

**100億 → 200億 → 2031年IPO。**
しかも98%創業者保有でVCゼロ。ステークホルダー型上場。

この戦略に技術が追いついていない。それが今の問題の本質。

### 技術側の現実（正直な評価）

| 項目 | 状態 | 深刻度 |
|------|------|--------|
| **システム構造** | PHP/C#モノリス。全機能が密結合 | 🔴 |
| **テスト** | 存在しない | 🔴 |
| **デプロイ可能な人数** | Web機能は2名のみ | 🔴 |
| **ドキュメント** | コードにコメントがない。暗黙知 | 🔴 |

| **AI活用** | 限定的。密結合がボトルネック | 🟡 |
| **インフラ** | 不明点多い（GCP? オンプレ? ハイブリッド?） | 🟡 |
| **モバイル** | Flutter採用済み | 🟢 |
| **内部ツール** | Retool活用中 | 🟢 |

事業戦略は9点。技術基盤は3点。このギャップが全ての問題の根源。

## CTOとしてのビジョン

### 一言で言うと

> **「本の循環データ」を世界で最も賢く使える技術基盤を作る。**
> その基盤の上に、6つの戦略が自然に乗る状態を実現する。

### ビジョンの全体像

```
2026                    2027                    2028-2031
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│  基盤を作る       │    │  基盤で稼ぐ       │    │  基盤を開放する   │
│                  │    │                  │    │                  │
│ ・書誌API        │    │ ・価値DB外部提供  │    │ ・出版業界の      │
│ ・データ正規化    │ →  │ ・推薦エンジン    │ →  │   共有インフラ    │
│ ・テスト文化     │    │ ・本棚スキャンAI  │    │ ・API経済圏      │
│ ・CI/CD整備     │    │ ・ポイント基盤    │    │ ・IPO準備        │
│ ・チーム拡大     │    │ ・プロAcc基盤     │    │                  │
└─────────────────┘    └─────────────────┘    └─────────────────┘
```

### ビジョン① — データを「資産」から「武器」に変える

**現状:** データは溜まっている。しかし活用されていない。

BQ調査で確認した事実：

| データ | 量 | 今の使われ方 | 本来の価値 |
|--------|-----|-------------|-----------|
| 書誌（m_shoshi） | 350万冊 | 商品表示用 | 日本最大の書誌インテリジェンス |
| 日販データ（nippan） | 348万冊（99.3%） | ほぼ未使用 | 著者・シリーズ・出版社の構造化データ |
| 現品（m_genpin） | 4,112万件 | 在庫管理用 | 状態別価格の時系列 = 価値予測エンジン |
| 買取・査定 | kaitori + satei | 業務処理用 | 需給予測。「今が売り時」の根拠 |
| 顧客 | 77万人 | 注文処理用 | 読書行動・ジャンル遷移のパターン |

**やること:**

1. **書誌インテリジェンスAPI** — ISBNを入れたら、タイトル・著者・シリーズ・市場価値・需給スコアが返る。まず社内で使い、後に外部提供
2. **価値データベース** — 4,112万件のgenpinから「この本は今いくらか」「3ヶ月後にいくらか」を即答するエンジン
3. **循環データレイク** — 買取→査定→在庫→販売→次の買取のサイクルを一気通貫で追跡できるデータ基盤

### ビジョン② — 6つの戦略に「技術のレバレッジ」をかける

経営戦略は決まっている。技術の仕事は、それぞれの戦略に **10倍のレバレッジ** をかけること。

| 経営戦略 | 技術のレバレッジ | 具体的に作るもの |
|----------|-----------------|-----------------|
| **① ポイント経済** | FinTech級の信頼性を持つポイント基盤 | 台帳API、残高管理、有効期限、消費税対応、不正検知 |
| **② グッズコラボ** | Shopify統合 + 在庫一元管理 | 本とグッズを同じカートで買えるUX |
| **③ SKYPOD** | リアルタイム在庫連携 + 予測的棚入れ | SKYPOD APIとの双方向連携、需要予測による自動補充 |
| **④ 本棚スキャン** | 画像認識AI + 即時査定 | カメラ→ISBN認識→価値DB参照→即時見積もり |
| **⑤ プロアカウント** | セルフサービスAPI + ダッシュボード | 著者・出版社が自分で出品・価格設定・売上確認できるプラットフォーム |
| **⑥ メディア** | コンテンツ×コマースの融合 | 動画で紹介した本をワンタップで買える導線 |

### ビジョン③ — 「作り直し」ではなく「積み上げ」で進む

案3（フルスクラッチ）の方向性は正しい。
しかし **「旧を壊して新を作る」のではなく「新しい価値を積み上げて旧を不要にする」** アプローチを取る。

```
             旧システム（モノリス）
             ┌──────────────────────┐
             │ 買取・在庫・販売・モール │
             │ （動いている限り触らない）│
             └──────────┬───────────┘
                        │ 読み取り
                        ▼
             新サービス群（独立して構築）
             ┌──────────────────────┐
             │ 書誌API → 価値DB →    │
             │ ポイント基盤 →         │
             │ 読書プラットフォーム →  │
             │ プロアカウント基盤      │
             └──────────────────────┘
                        │
                        │ 新サービスが十分成熟したら
                        ▼
             旧機能を一つずつ統合
             （ストラングラーフィグパターン）
```

**理由：**
- 旧システムは今日も売上を生んでいる。止めるリスクを取る必要がない
- 新しいものを作る方がチームのモチベーションが高い
- 各フェーズが独立して価値を持つ。途中で止めても成果が残る
- BQパイプラインへの影響が最小限（13_整合性分析の懸念3,4が解消）

### ビジョン④ — AIが「道具」ではなく「開発の主体」になる

中村さんの言葉通り「AIがコードを書き、人は承認だけ」を本気で実現する。

**そのために必要な条件：**

| 条件 | 今 | 目標 |
|------|-----|------|
| テスト | ない | 全新規コードにテスト必須。AIが書いたコードもテストが検証 |
| 型 | BQもDBもSTRING | 型付き言語 + 型付きスキーマ。AIが安全にコードを生成できる |
| API仕様書 | ない | OpenAPI / GraphQL スキーマ。AIはこれを読んでクライアントを自動生成 |
| CI/CD | ない | マージ前に自動テスト。AIのPRも人のPRも同じ品質ゲートを通る |
| ドキュメント | 暗黙知 | ADR（Architecture Decision Records）で設計判断を記録 |

**新規開発のワークフロー：**
```
要件（人が定義）
  → 仕様書（AIが生成、人がレビュー）
    → コード（AIが生成）
      → テスト（AIが生成）
        → CI/CD（自動実行）
          → デプロイ（人が承認）
```

### 採用の優先順位

**第1位: テックリード / アーキテクト**

なぜ最初にこの人が必要か：
- 新システムの全体設計を決める人がいない
- API設計、DB設計、技術選定の意思決定者
- 後から入るメンバーの「土台」を作る

**第2位: SRE / DevOps**

なぜ2番目か：
- CI/CDがなければ、AIを活用した開発ワークフローが成立しない
- テスト文化の導入は、ツールと仕組みが先
- この人がいないと、開発速度が上がらない

**第3位: データエンジニア**

なぜ3番目か：
- BQ→新DBのパイプラインは全プロダクトの基盤
- 書誌APIの構築を実際に手を動かして進める
- 既存データの型変換・正規化は専門性が必要

## スキル獲得の方法

採用だけが答えではない。

| 方法 | 対象スキル | メリット | デメリット |
|------|-----------|---------|-----------|
| **正社員採用** | テックリード、SRE | チームの核になる。長期的な判断ができる | 時間がかかる。上田原では採用難 |
| **業務委託** | データEng、ML、フロントエンド | 即戦力。Phase別に調整可能 | ドメイン知識が溜まりにくい |
| **AI活用の最大化** | コード生成、テスト生成、ドキュメント | 人数を増やさずにアウトプットを増やす | 設計判断はAIには任せられない |
| **既存メンバーのスキルアップ** | DevOps、テスト、API設計 | ドメイン知識がある人が新スキルを習得 | 時間がかかる。日常業務と並行は難しい |
| **外部アドバイザー** | アーキテクチャ、セキュリティ、FinTech | 専門知識をピンポイントで得られる | 常駐しないため実装力にならない |

### 推奨する組み合わせ

```
テックリード（正社員） ← 最重要。この1人が全体を決める
SRE（正社員 or 長期業務委託） ← 基盤を作る人は中長期で必要
データEng（業務委託スタート → 正社員化） ← まずPhase 0の書誌APIを一緒に作る
MLエンジニア（業務委託） ← Phase 1の本棚スキャンAIで必要になるタイミングで
フロントエンド（業務委託） ← Phase 2のUI構築で必要になるタイミングで
AI活用 ← 全フェーズで。人を増やす前にAIで倍率をかける
```

## 技術選定の方針

### 新システムの推奨技術スタック

| レイヤー | 技術 | 選定理由 |
|----------|------|---------|
| **言語（API）** | Go or TypeScript (Node) | Go: 既存知見あり、高速。TS: AIが最も得意な言語、フロントと共通化 |
| **API仕様** | OpenAPI 3.1 + GraphQL | REST APIをPro Account向けに公開、GraphQLは内部フロント向け |
| **DB** | PostgreSQL | 350万冊の書誌 + JSONBで柔軟な属性管理。実績豊富 |
| **検索** | Meilisearch or Elasticsearch | 書名・著者の全文検索。日本語対応 |
| **キャッシュ** | Redis | セッション、ポイント残高、在庫数のリアルタイム参照 |
| **メッセージング** | Cloud Pub/Sub or NATS | イベント駆動。在庫変動、価格変動の通知 |
| **インフラ** | GCP (Cloud Run + Cloud SQL + BQ) | BQ既存利用。Cloud Runでコンテナ運用 |
| **CI/CD** | GitHub Actions | AI PRも人のPRも同じパイプラインで品質担保 |
| **監視** | Datadog or Cloud Monitoring | SLI/SLO管理。SKYPOD連携の遅延監視 |
| **フロントエンド** | Next.js (React) | SSR対応、SEO重要（書誌ページは検索流入が命） |
| **モバイル** | Flutter（継続） | 既存資産を活かす |

### 技術選定で大事なこと

**「最新」よりも「AIが書きやすい」を優先する。**

AIがコードを生成する時代において、技術選定の基準は変わった：
- 学習データが豊富な言語・FWを選ぶ（Go, TypeScript, Python, React）
- 型がある言語を選ぶ（AIが型エラーで自己修正できる）
- テストが書きやすいFWを選ぶ（AIが生成したテストでAI生成コードを検証する）
- ドキュメントが豊富なエコシステムを選ぶ（AIがドキュメントを読んで学べる）

## 最後に：CTOとして最も大事にすること

### 1. 事業の邪魔をしない

技術のリファクタリングや移行に夢中になって、売上を止めるようなことはしない。
旧システムは動いている限り、そのまま動かす。
新しいものを横に置いて、自然に置き換わる設計をする。

### 2. 小さく始めて、早く見せる

6ヶ月計画を立てて、6ヶ月後に「できました」と言うのではなく、
2週間で動くものを見せて、フィードバックをもらって、また2週間で改善する。

書誌APIは2〜4週間で動くものが作れる。それを見せた時に全員の景色が変わる。

### 3. データで議論する

「この機能は必要だと思う」ではなく
「この機能を使っているのは月間○○人で、売上への貢献は○○円」で話す。
BQにデータがある。使い倒す。

### 4. 人を増やす前に仕組みを作る

テストがない状態で10人採用しても、10人が同じバグを作る。
CI/CDがない状態でAIを使っても、壊れたコードが本番に入る。
まず仕組み。次に人。

### 5. 「本が好きな人」のためのプロダクトを作る

技術は手段。目的は「本の循環を加速し、読者と本の出会いを最大化する」こと。
Amazonが効率で勝つなら、バリューブックスは **愛着** で勝つ。
「この本はあなたの前に2人が読んで、どちらも手放さなかった。3人目のあなたが初めて手放した。そして今、4人目の読者のもとへ。」
—— こういう体験を技術で可能にする。
